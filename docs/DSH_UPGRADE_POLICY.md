# DSH 依赖维护与受控升级

当前内嵌运行时仍以 `tests/contract/dsh-pin.json` 和 `vendor/dsh-runtime/VENDOR-MANIFEST.json` 为准（`0.1.0-rc.5 @47f943859bef60e4160492346772ded9b24f765a`）。M0-1b 已移除旧 alpha.2 候选宿主、插件、构建与 `dsh:upgrade` 入口；正式 pin 与 vendor 未变。旧候选实现可从 Git 历史查阅，运行目录未迁移或删除。

后续升级按下面的原则在独立候选中验证；当前没有自动升级命令。项目路线与进度以 `PLAN.md`、`STATE.md` 为准。

## 1. 已确认原则

WeftMate 复用 DSH，但不自动跟随每次上游更新。固定一个可追溯版本；影响安全/稳定性的修复优先评估，确实需要的新能力安排接入，无关变更不追着升级。固定版本不是永久不维护。

应用使用其内嵌 vendor；用户另装的 DSH 更新不会自动改这份运行时。WeftMate 更新也不必每次变更 DSH。MemoWeft、Mod 是否受影响，看接口和数据变化，不要求所有项目同步重写。

## 2. 三种资产分别核对

| 资产 | 路径 | 意义 |
| --- | --- | --- |
| 固定版本记录 | `WeftMate/Repository/tests/contract/dsh-pin.json` | 要验证的仓库、包版本和提交。 |
| 内嵌产物清单 | `WeftMate/Repository/vendor/dsh-runtime/VENDOR-MANIFEST.json` | 实际打包来源、依赖闭包与哈希；应用用这一份产物。 |
| Shared 源码 | `Shared/Dependencies/DeepSeekHarness` | 导出的工作树，含原本未提交改动；不保证全部进入内嵌包。 |

此快照前两者记录 `0.1.0-rc.5 @ 47f943859bef60e4160492346772ded9b24f765a`，以实际文件为准。显示版本号相同也未必是同一提交/同一产物；不同来源不可互相代替。原包没有 .git，不能伪造 checkout（仓库工作副本）骗过 pin 校验。

## 3. 变更成本分类

内部修复而接口不变：更新候选产物并回归，不一定改业务。新增功能：升级只是提供基础，还需启用/连接和必要前端。接口、事件、页面扩展或存储变化：集中适配，必要的数据迁移单独测试。

前端、记忆和 Mod 尽量通过稳定公开能力与集中连接代码使用 DSH；不在每个页面直接依赖私有文件和状态，不把所有业务嵌进上游。不保证未来永不适配。必须修改上游时列最小补丁及测试，定期判断是否能上游合并/删除。

## 4. 升级前给用户看的小任务卡

```text
为什么需要这次升级：修了什么 / 我们需要哪项能力 / 不升级的影响
当前固定提交、内嵌清单与实际本地修改：
拟定目标提交及官方变更依据（到时现查，不猜“最新”）：
可能受影响：对话 / 记忆 / 插件 / 权限 / 页面 / 数据
计划改哪些连接，不改哪些功能：
独立代码目录与测试数据副本：
开发者测试、用户的 D01—D03：
失败时旧程序 + 哪份匹配数据恢复：
授权与停止点：
```

用户同意后在独立候选中执行，不在日常运行目录直接拉取并覆盖。安装依赖的网络与脚本副作用需说明；读取用户数据/付费模型不是升级许可的自动部分。

## 5. 升级步骤与检查

1. **记录基线**：当前源码/pin/vendor/工具链、所有上游私有改动和当前已验收能力，备份测试配置与一致性数据。保留日常版本。
2. **核对目标**：从官方源核对准确提交和变更，在干净独立 checkout 准备；不可丢原 Shared 未提交改动。目标已有缺陷或不兼容时先评估，不只看版本号大。
3. **先适配验证**：检查初始化、模型路由、会话/消息来源、记忆交接/召回、工具注册/审批/取消、客户端扩展、插件启停、错误状态。按本轮已有能力选择，不将未实现项目伪装通过。
4. **检查构建与数据**：恢复锁定依赖和工具链，检查契约和 vendor，再生成候选。旧会话/配置/附件/凭据引用在副本中验证；不要把密钥打印到诊断。
5. **用户试用**：D01—D03 与受影响功能用例；开发自测通过后仍是“待用户试用”。
6. **发布或恢复**：仅在通过后替换日常版本；失败保全证据、暂停候选，恢复旧应用与对应旧数据。更新 CURRENT_STATE 和 WORKLOG，记录 pin/vendor 来源。无发布授权就只交候选。

契约测试绿不等于真实产品绿；有脚本不能代替上述检查。先修前端、先恢复环境、先升级 DSH 不应同时在一个任务发生；确实有因果依赖时先说明并拆成可回退顺序。

## 6. 数据回退的真实含义

程序回退和数据回退分开。新版写过的数据可能不被旧版支持。记录 schema 变化、是否可逆、备份时间、哪些新数据可能不能带回；绝不直接拿旧程序反复打开新数据试运气。

迁移在测试副本验证，停止/崩溃中断和重试也检查。恢复的是匹配旧版本的数据副本，避免覆盖用户新的正式资料。真实外部动作（发消息等）不属于代码回退能够撤销的范围。

## 7. 现有构建入口

`npm run vendor:dsh` 按固定 pin 生成内嵌产物，`npm run vendor:verify` 核对已有产物；它们不负责选择新的 DSH 版本。旧 alpha.2 候选升级入口已删除。新的升级工作包需要准备自己的隔离候选和兼容验证。

## 8. 成功记录必须含什么

旧/新精确提交，vendor 清单指纹，保留或去掉的本地补丁，工具链、测试命令与结果、失败/未测、用户反馈、数据恢复演练、最终候选/发布标识。写入记录后可复查，不依赖聊天声称“升级过了”。
