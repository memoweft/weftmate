## 2. 规则

1. **先验收，再动手。** 开工第一件事是按 PLAN 的记忆场景（M1–M7）跑一遍，结果记进地图第 4 节。两种环境都要跑：全新安装的 Windows 安装包（合成账号），以及开发模式下带记忆配置的宿主（合成数据）。跨端场景注明实际参与的设备；缺少环境时记阻塞，不能用宿主单测代替手机验收。本人自己的安装版只在本人在场时只读核对，不改它的数据。
2. **不碰本人的日用数据。** 测试用独立的数据目录和合成账号。本人安装版用到的那份 MemoWeft 源码目录（位置见本机 `MACHINE.md`）不切分支、不改文件；改内核用单独的工作目录。
3. **记忆内容不外露。** 日志、PR、截图和问题单里不出现真实的记忆内容，只写条数、状态和合成例子。
4. **打包方式已定为 A（D106），默认完整语义层（D110）。** 安装包携带受管 Python、MemoWeft 和必需依赖，两层仍能单独构建，固定版本、散列与许可，用户端不安装依赖。保留显式已有配置的兼容性；运行时与数据目录分开，组件更新不能覆盖用户记忆。组件分发、自动接线、安装升级验收依次完成，构建方法和限制见 [组件说明](../scripts/memory-runtime/README.md)。方案比较保留在第 5 节，不再重复询问这项决定。
5. **可靠性放进内核，不在 WeftMate 这一侧再叠层。** 不再新增队列、日志、恢复补做这类层。遇到失败，先复现、先写一条会失败的测试，再判断原因在哪一层：内核缺原子性或幂等，就改 MemoWeft（在它自己的仓库，走它自己的 PR），WeftMate 这侧只做同步调用。确实要在 WeftMate 这侧加，在 PR 里写清复现步骤和为什么不能放进内核。
6. **删除语义照 D16、D33。** 忘掉一条记忆包含整条修订链及其来源，确认前列出连带条目；独立的其他话题和默认保留的聊天原话不动。同批最新指令一起核对，取消先于命令提交就不删除；已提交的命令以 Core 实际回执为准，只有确认成功才能说「已经忘了」。纠正也必须关联真实消息原话，模型改写只是提议；宿主核对 Core 的来源能力，由 Core 复用该消息的来源、逐字片段和形成规则。
   整句核对过长或失败时不删，不得截断后重新授权；长消息即使只有明确遗忘也按相同边界停下。旧请求恢复（含定时、重启和冻结计划复用）须重新核对保留的完整原话，不沿用保存的授权；原话缺失、过长、无法核对或授权范围变化时，停止并要求重新确认。已有命令只查询原回执，结果不明时保留原身份和不确定状态，不重放删除。记忆页选中的未形成独立来源，以完整来源本身核对权限、归属和完成性，不因没有正式条目而一律拒绝。混合来源还包含目标内容且必须保留独立事实时，本批按[经理确认](https://github.com/memoweft/weftmate/issues/332#issuecomment-6221354361)安全停止：预提交不执行，已有真实成功回执仅报部分完成；旧命令结果不确定时保留原身份等待核对，不说从未执行。M3仍失败，不能用隐藏来源、擦词或误删独立事实代替真正遗忘。Core有界来源清理须另交设计并在安装版验过，本批不实现，也不默认启用记忆。
7. **接口变化要同步。** 改 `/personal/v1/memory` 下的路由，同时改 [CLIENT_API.md](CLIENT_API.md) 和安卓白名单（`Network.kt::validBusinessPath`、`BusinessRouteUnitTest.kt`）。
8. **真实内核的测试进 CI 名单。** 新增接真实 MemoWeft 的测试，加进 `observed-core` 的文件名单。内核修复先在 Core 合入主线并通过主线检查，再用独立 PR 更新这里的 `ref`，按当前名单复验；已有的随包运行时固定版本须同时保持一致，并在 PR 里说明。
9. **范围。** 只改上表里的记忆文件和 MemoWeft 仓库，界面只改记忆页。别的端、别的功能有问题，记下来交给总代理。
10. **先看在途的工作。** 开工前查 GitHub 上打开的、动到记忆的 PR，不要并行重写同一块。2026-10-15 在途的有 FIX-50（遗忘）和 APPLE-14（iPhone 单机记忆）；APPLE-14 属于后续平台（D101），不在这条轨道里。
11. **收尾时落盘。** 新结论写进这一页或 DECISIONS，不留在对话里；地图第 4 节记忆那一行同步更新。

## 5. 安装版记忆打包方案（2026-10-15，已选 A）

**本人已选择 A：在程序中携带受管的 Python（解释器）、MemoWeft 和必需依赖。** 保留已经验证的进程调用接口；程序按安装位置定位自己的运行时，用户不用装 Python、不用有源码目录，也不修改系统 Python。旧安装配置继续兼容，现有数据不随组件更新覆盖。

体积基准：本轮本机记忆环境的 `site-packages` 共 17,024,429 字节，其中开发安装工具 pip 占 11,349,634 字节；其余约 5.7 MB。该数值不含基础解释器和 Core 源码，也未安装语义检索的可选依赖，**不能当作最终安装增量**。下表体积是工程估算，选定方式后以实际构建测量；语义检索的 ONNX（模型交换格式）运行时、分词器和模型资源须单列，不把缺组件冒充完整记忆。

| 方案 | 体积与运行方式 | 更新与失败时的体验 | 工作量与取舍 |
|---|---|---|---|
| **A · 程序内置受管 Python + Core（推荐）** | 基础组件预计为几十 MB 量级；语义组件和模型资源另算。使用独立子进程，沿现有 RPC（进程调用协议）。 | 随程序版本校验和更新；启动失败时保留聊天与记忆数据，明确提示修复记忆组件。无需首次联网下载解释器。 | 较低到中等：固定依赖、打包、自动配置、迁移与安装验收；当前核心行为保留，适合本阶段收稳。 |
| B · Core 打成独立可执行程序 | 仍包含解释器及依赖，通常与 A 同一量级，不会自动变成一个极小程序。优先目录形式。 | 独立组件版本随应用发布；需处理动态模块和数据资源遗漏。单文件形式启动会先解压。 | 中等：还需冻结模块发现、资源和进程启动方式；收益主要是分发形态统一。 |
| C · 首次使用时下载记忆组件 | 主安装包增加较少，首次下载和安装后的总占用接近 A/B；语义资源仍另外计量。 | 需要下载、校验、失败重试和离线提示；下载未完成时聊天可用，明确告知暂不能形成完整记忆。 | 中等：增加首次下载和组件修复流程；会多出一条影响“装好就能记住”的失败路径。 |
| D · 将 Core 移植到 Node.js（脚本运行时） | 可省去 Python 基础运行时；数据库、语义推理库和模型资源仍可能需要额外体积。 | 跟随主程序更新，但必须证明旧数据、形成、纠正、遗忘和来源语义兼容。 | 很高：属于内核迁移，需要重新验证现有行为；不建议在收稳阶段开展。 |

Python 官方提供用于嵌入应用的精简分发，并建议由应用管理第三方依赖；这里采用独立随包运行时，不调用用户系统里的默认解释器。[Python 官方说明](https://docs.python.org/3.14/using/windows.html#the-embeddable-package)

PyInstaller（Python 程序打包工具）也会携带解释器和依赖；目录形式便于检查，单文件形式增加启动解压步骤，因此不能仅凭“单个 exe”判断体积或可靠性更好。[PyInstaller 官方说明](https://pyinstaller.org/en/stable/operating-mode.html)

方向已确认，后续按规则 1 和做完标准验证；方案选择本身不代表安装包已经具备记忆。
