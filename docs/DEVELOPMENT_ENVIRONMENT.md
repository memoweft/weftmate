# 开发环境与多端验证安排

> 本文件采用用户指定累计包中的方向与安排。包内实现描述不代表本机已合并或验证；本机进度唯一见 CURRENT_STATE.md。2026-09-08 清理按用户要求不备份，旧归档不再作为开工材料。
来源：用户本轮指定的 2026-09-06 累计包中的设备与验收安排，2026-09-08 归入实际仓库。下列设备信息为附件记录，未在本轮逐台核验；没有登录设备、连通服务器或运行模型。

本文件只维护环境约束、分工建议与验证方法，不维护第二份全局进度。当前任务只看 [CURRENT_STATE.md](CURRENT_STATE.md)；下文设备安排不是已经执行的多端验证结果。

## 1. 附件记录的设备与约束

- 有一台 macOS / Windows 11 双系统笔记本；另有 Windows 台式机，当前主要跑本地模型。
- WeftMate 是独立产品，并且必须在 Windows 上验证，不能将 Windows 台式机只当计算机器。
- 长期希望 macOS、Windows、Android、iPhone 与手表都能使用 WeftMate。目标平台不等于当前全部已有客户端或已可运行。
- 已有 Root Android 手机、Android 平板、iPhone、Apple Watch 与蓝牙耳机，可作为相应场景的未来验证设备。
- 已有美国服务器，用户明确其主要用途是代理，次要用途是官网。没有确认将私人记忆、对话、健康数据或助手运行后端部署到那里。
- 用户想先理顺自己的开发工作流，再逐步把个人助手做出来。

“独立项目”不意味着禁止组合 MemoWeft 和 WeftMod。后续已明确的产品关系继续有效：WeftMate 是主程序，MemoWeft 是共享长期理解，WeftMod 提供可选能力。旧助手将独立项目解读为不能整合的表述不继续采用。

## 2. 私人环境记录放哪里

具体设备型号、系统原话、服务器地址和本机路径属于用户环境资料，不是产品通用默认值。公开源码不写死个人地址，不复制完整设备画像。

附件未包含私用设备明细；实际需要时可将用户提供的私用记录放到主仓库 `.local/DEVICE_ENVIRONMENT.md`，或工作区已有的私密资料区。现有 `.gitignore` 已忽略仓库根 `.local/`，但这不能删除已提交的历史；开发者提交前仍须检查实际待提交文件。读取设备说明不等于得到网络访问、控制手机或健康采集授权。

用户提供的 CPU 名称与系统版本按原话保留，不根据旧记忆或型号相似度擅自纠正。S00-B 中开发者可在用户给定范围内只读核对并记录差异；未核对不是要求用户重新口述的理由。

## 3. 分工建议：尚非用户已经完成的配置

| 设备角色 | 建议用途 | 边界 |
|---|---|---|
| 双系统笔记本的 macOS | 日常讨论、审设计、看代码、文档、Git；条件允许时作为远程工作入口；后续原生 macOS 体验验证 | 日常主系统选择仍是建议；远程看到 Windows 画面，不算 macOS 客户端通过。 |
| Windows 台式机 | 继续运行本地模型；作为当前 Windows 依赖路径的开发与原生验收机器 | 候选、数据目录、端口与进程同日常模型分开；不能因退出候选而误停原模型。Windows 具体版本待只读核对。 |
| 笔记本 Windows 11 | 阶段版本在第二台 Windows 环境验证安装、启动、退出与已交付流程 | 不要求每改几行都重启切系统；同一笔记本双系统通常不能同时作为两台在线机器。它是第二环境，不自动等于干净环境。 |
| Android 手机 | 后续 Android 客户端体验和经授权的 WeftMod 低风险设备操作 | Root 是现有条件，不是无限权限或默认调用真实账号的授权；不能据此宣称普通非 Root 设备兼容。 |
| Android 平板 | 后续平板布局、阅读、触控与接续体验 | 不复制另一套用户记忆或模型服务；页面尚未实现时不要求测试。 |
| iPhone | 后续移动输入、查看任务、重要确认与通知体验 | iPhone 上使用助手与助手能任意控制 iOS 是不同能力，不能混用。 |
| Apple Watch 与耳机 | 已实现相应能力后验证短提醒、简短输入、收音和播放 | 硬件已存在，不代表语音、健康接口或手表应用已实现。 |
| 美国服务器 | 保持用户指定的代理与官网用途 | 本轮不新增助手服务、传输私人数据、改 DNS、开端口或部署任何程序。 |

推荐的起步组合是“笔记本作为操作与审阅入口，Windows 台式机作为当前程序验证与模型机器”，而不是把所有设备都安装成一套完整开发中心。这一分工为助手建议；远程方式、开发主系统和常驻服务位置没有被本文件暗中批准。

## 4. 先管住代码和数据，再谈多端同步

每个任务明确：在哪里编辑、在哪里运行、在哪里存测试数据、怎样对齐候选版本。

- 同一任务只指定一个主要可写工作区。修改当前 Windows 相关代码时，建议在 Windows 原生工作区执行，笔记本可远程操作它；不依赖两台机器各改一份再互相覆盖。
- 需要 macOS 原生检查时，使用同一已记录候选的独立 macOS 工作区。通过 Git 提交或明确的补丁清单对齐代码；未提交内容也必须被记录。没有真实 Git 的 ZIP 不伪造提交号。
- 配置、依赖和生成物按平台独立恢复；不跨系统复制整套已安装依赖。不要把运行中的个人数据库当代码交给普通目录同步，也不通过 Git 同步私人记忆。
- 开发版、候选验收版与日常运行数据隔离；每次测试写准路径。重启测试使用同一份隔离测试数据；升级测试保留配套旧数据副本。
- 当前尚未交付用户级多端数据同步、离线缓存或自动排队。下面的跨端目标不能成为已实现功能描述。

## 5. 产品安排：共享理解，但分开计算和动作位置

目标是各端面向同一用户协作，而不是每一端重建一个独立助手。设计时分别说明：哪一处记录是准的、模型请求去哪一台机器、操作实际在哪台设备执行。

例如未来用户在 iPhone 提问，可由获授权的入口请求 Windows 台式机上的本地模型，并将获授权的手机任务交给指定 Android 设备。此处仅说明目标关系；认证、联网、路由、数据同步和执行授权尚未因本文件而实现。

台式机休眠、关机或模型不可用时，不能继续宣称已经完成。如何显示离线、允许哪些缓存或暂存、是否允许云端补位，需在对应任务中明确；默认不静默切云端，也不把代理服务器当必然可用的助手后端。

各端共享的是必要的理解和任务信息，不代表每端都必须保存全部私人数据；手机、手表也不必承载完整桌面界面。未来设备状态/健康数据另有来源、时效和授权边界。

## 7. S00-B 的 3 项用户检查（未开工模板）

开发者先准备可运行的独立候选和准确入口，并核对原模型服务的进程；依赖修复、端口检查和日志分析由开发者承担。

1. 打开候选，确认是哪台机器、哪个系统、什么候选版本及哪份测试数据，没有混入私人记录。
2. 找到已存在的插件设置，区分已加载、待重启、未配置与尚不能执行。没有新增手机任务或打开真实采集。
3. 完整退出候选，确认本次窗口和受管进程收尾；台式机原本的本地模型服务及其他程序不被误停。由开发者核对进程，不让用户全局结束任务。

同一轮交付卡附 Windows 与 macOS 的结果栏。macOS 尚未准备可执行入口就写阻塞/未测，不让用户盲跑，更不靠远程 Windows 截图替代原生验证。用户反馈后修当前项，未通过不自动继续。
