# S4 云端备份验收证据

**这里的恢复码全部属于本机随机端口合成云、合成账号和临时资料目录，不是真实使用者的恢复码。** 每次验收重新生成，合成云和临时资料在结束后清理。截图里的模型凭据也是合成值；真正的 MiMo API（应用接口）密钥只从机器环境读进验收代理进程，既不进入桌面保管库，也不进入备份、截图或日志。

`tests/integration/s4-cloud-backup.mjs` 运行真实 Electron（桌面程序框架）、生产 `src/main.mjs`、固定 DSH（原生助手运行时）和系统加密凭据库。隔离启动脚本只控制程序重开、合成保存文件路径／打印操作，以及测试固定的私人网络接电条件；没有替换凭据库或伪造记忆。对话与记忆使用云端 `mimo-v2.6-flash`，模型目录在本次代理进程内缓存，避免状态读取重复访问云端目录。

桌面截图分别使用浅／深主题、1200／480 CSS（界面布局）像素宽度，高度 800；Windows（视窗系统）显示缩放会使 PNG（位图）像素尺寸成比例增加。所有弹层都拍打开状态。文件名为 `desktop-<宽度>-<主题>-<状态>.png`。

| 状态后缀 | 场景 |
|---|---|
| `enable-recovery-code` | 同一弹层显示恢复码、遗失后果、密钥包含范围及抄写确认 |
| `enabled-status`、`backup-status` | 原电脑设置中的备份状态和空间 |
| `new-computer-restore-prompt` | 全新资料目录登录同账号后，应用内的可关闭恢复提示 |
| `restore-code-input`、`restore-completed` | 输入恢复码与恢复后核对 |
| `wrong-recovery-code` | 抄错一组时指出组号；当前数据保持完整 |
| `corrupted-backup`、`download-interrupted`、`newer-version` | 合成密文损坏／连接中断／更新版本备份时的真实程序错误处理 |
| `upload-interrupted`、`upload-resumed` | 第一块确认后结束真实程序，重开继续同一份备份 |
| `quota-exceeded` | 合成云实际配置 5 MiB（兆字节）上限，保留前两份后追加 1 MiB 随机文件，自然触发第三份整包预留拒绝；生产默认 300 MiB 由固定测试保护 |
| `single-backup-actions`、`single-backup-delete-confirmation` | 单份操作与删除确认弹层；取消操作 |
| `forget-protected-status` | 只有电脑的合成账号通过正式记忆遗忘接口删除一项；旧云备份清除，旧待传包丢弃，重新捕获当前状态 |
| `delete-confirmation`、`deleted-status` | 删除全部云备份与零剩余记录核对 |
| `old-cloud-unavailable` | `c1e96a36` 的真实结构 9 云源码；仅显示暂不可用、备份请求为零 |

`verification.json`、`verification-old-cloud.json`、`verification-wire.json` 分别保存真实恢复主链、旧云兼容、完整上传补验的实际核对、模型请求数及清理结果。只有 `status:"passed"` 的报告表示对应场景通过。尝试过程和累计模型请求数记录在不提交的 `.local/s4-attempts.jsonl`，最终交付汇总全部尝试。`failure*` 只用于诊断，交付时移除。

本次分阶段续验复用了已形成的真实对话、3 条认知记忆及已上传的首包，避免重复模型调用；主链累计实际模型请求 **19 次**，尾段与旧结构 9 阶段均为 0 次。失败后的已停止合成资料保留用于续验；切换合成云时走正式解绑／认领／绑定接口，保留会话、记忆、模型及系统凭据库。持久合成云的 `file`（文件）邮件限流计数在续验夹具初始化时重置，以免多次调试的验证码请求遮挡备份流程；备份接口限速和生产默认配额的固定测试照常保留。

主链续验沿用了已上传的 47,622 字节首包。其最终 `wireScan.bytes=3300` 仅是只读续验阶段的钥匙／清单请求，**不包含再次上传的密文块**。主链还扫描了当时全部保留的数据库密文，特征句和合成模型密钥均零命中；该阶段的密文字节总数没有单独保留。

合入 `main` 后，`WIRE_ONLY`（完整上传补验）使用另一组全新合成账号、云端和真实 Electron 资料目录，通过正式账号／模型接口保存合成模型密钥，通过正式会话命令与元数据接口保存特征句，然后启用并完整上传一份备份。该过程不发模型推理请求，模型目录真实请求 1 次、其余 16 次读取使用缓存。`verification-wire.json` 对这次完整上传记录了精确计数：

| 扫描对象 | 字节数 | 合成特征句／合成模型密钥／恢复码 |
|---|---:|---|
| 全部备份原始请求体 | 44,827 | 三者均零命中 |
| 解码后的签名载荷 | 30,292 | 三者均零命中 |
| 全部上传密文 | 18,041 | 三者均零命中 |
| 云数据库全部备份密文 | 18,041 | 三者均零命中 |

该份备份共 1 块，上传密文和数据库密文均与完成清单的总字节数一致。补验结束后，新资料目录登录并显示恢复提示，验证最终 KB 大小文案。`enable-recovery-code`、`backup-status`、`new-computer-restore-prompt`、`restore-code-input` 的四种主题／宽度截图由这个最终补验覆盖，共 16 张；其余 60 张保留真实恢复、错误处理、断点续传、遗忘、删除和旧云兼容场景。这次补验提供完整上传字节和最终文案证据，真实 MiMo 恢复与继续对话仍由主链报告证明。

主链比较恢复前后的会话、认知记忆文本／标识／条数、通知和个性化设置、模型配置及保管库中的合成凭据，并在恢复后用实际 MiMo 继续同一对话。全部删除后核对清单、密文块、包裹钥匙和额度均为零。

运行边界：只访问脚本创建的随机回环端口与已授权 MiMo 接口；不访问生产云、不向 18186 请求、不控制本人桌面、不读取日用数据。保存文件与打印使用测试替身，系统原生对话框留待本人试用时确认。
