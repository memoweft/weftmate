# QA-3 问题清单

**是否建议本人开始试用：否。** 正常手机使用流程会被错误的离线页反复遮挡；王小明的确认决定没有形成正式记忆；迁移脚本的 Verify 在已启动宿主上返回 401。Apple（苹果客户端）本轮结果与覆盖范围见 README，没有使用 A12 / A13 的历史成绩代替本轮验收。

**可以迁移本人日用程序到安装版：否。** 安装、热更、差分升级、自动坏版回退与卸载保留数据已通过，但迁移验证脚本和完整跨端使用链仍有阻断。指定备份只在隔离副本上演练，未操作日用计划任务、18186、8081 或原运行数据。

## 阻断 · QA3-B01 · 在线手机误入离线页，遮挡任务审批、设置与项目

- **端**：MuMu Android（安卓模拟器）原生包、手机网页；桌面宽窗口不启用此入口。
- **步骤**：全新合成云账号注册；真实桌面登录并批准手机；手机连接电脑；配置 MiMo，手机要求电脑创建合成文件。此时宿主任务、历史和审批仍可正常读取。
- **实际**：全屏“离线模式”覆盖待批准任务，批准按钮被 `offline-messages` 拦截，30 秒点击超时。点真实“返回”后可继续，但下一轮刷新又弹出。两次恢复运行各记录 2 次干扰；完整中继手机网页也需要返回 1 次。设置逐页返回后能打开浅深 22 项，但项目新对话又被覆盖。第二账号隔离检查已通过，切回原账号时手机的设备允许按钮同样被遮挡。
- **期望**：在线状态继续办事；副本同步或授权错误显示对应错误，不将其改称电脑离线，更不能反复覆盖当前工作。正常同步应能通过既有认证与正文契约。
- **已定位**：`src/personal-access-ui/app.js` 和 `apps/mobile-ui/www/components/cloud-account.js` 的 `WeftOfflineView.mount` 传输回调遗漏 `protectedWrite:true`，且把 `body` 提前 `JSON.stringify`；`src/ui-core/shell.js::requestJson` 再次编码。隔离真实 HTTP（网页传输协议）探针复现正文为字符串、无 CSRF（跨站请求伪造防护）头、返回 403；使用对象及受保护写入的对照跨过该拒绝，进入故意无效公钥的 400 检查。`components/offline.js::tick/paint` 又把同步失败转换为 `offline=true`；返回只暂时隐藏，15 秒轮询重新显示。
- **截图**：[首次审批被遮挡](android/android-task-approval-light.png)、[中继同类故障](relay-retry/mobile-web-unexpected-offline-1-light.png)、[项目阻断](android-settings-final/extra-checks.json)。首次截图是真实安卓屏幕，没有强制点击或移除遮挡层。
- **记录**：[首次失败](android/android-visual-verification.json)、[恢复后任务](android-recovery/phone-task.json)、[完整中继](relay-retry/mobile-web-visual-verification.json)、[真实传输探针](offline/production-transport-proof.json)。
- **边界**：独立 M3-A 运行器提供了正确的测试传输，网页和安卓离线引擎闭环通过；这不证明正常产品接线通过。原始报告顶层 `passed:true` 只覆盖原运行器的任务检查，不能覆盖 `extraChecks` 里的项目失败。

## 验收阻断，未证明为数据丢失 · QA3-B02 · 指定备份未展示可核对的原记忆

- **端**：Windows源码／安装版／源码回退，使用指定备份的隔离副本。
- **步骤**：先核对原本地账号，再对副本中全部保存的账号身份设置仅测试用的本地登录替身；逐账号读取 entity、relationship、cognition 三类当前记忆。
- **实际**：三个启动阶段的原对话均可见，账号身份保留。原本地账号三类查询返回200但当前列表为空；其他保存账号的三类查询返回503，未能读取。初次仅查认知的记录单独保留，最终覆盖全部账号和三类。未导出任何原文、姓名、账号标识或记忆内容。
- **期望／剩余工作**：迁移前应明确预期原记忆属于哪个数据源，并在安装版核对。此次没有取得“原记忆可见”的正向证据。
- **边界**：源码启动时也有同样的空列表／不可用，故**不能称安装升级丢失记忆**；503也不能解释成记忆不存在。恢复后的副本和原备份66,050文件逐文件均为新增0、删除0、更改0；原日用数据未接触。
- **证据**：[最终副本演练](installed/migration-report.json)、[本地账号三类补验](installed/migration-legacy-all-kinds.json)。个人备份不截图、不提交，结果只含布尔、HTTP状态和完整性统计。

## 严重 · QA3-01 · 已确认的组队决定未形成正式记忆

- **端**：Windows 真实 Electron（桌面程序框架）、DSH（助手运行时）、当前固定 Core（记忆核心）、MiMo；新对话换 LAN（局域网模型）。
- **步骤**：原王小明八步。用户说“王小明打游戏挺厉害，是我好兄弟”；助手提议以后组队提醒找他；用户确认“好，以后我想组队时，就提醒我找王小明”；等待原运行器的正式作业收敛，再换模型新对话询问。
- **实际**：人物、关系、评价及其来源存在，确认决定及来源不存在。确认作业终态为 `no_change`，原因 `assistant_claim_context_missing`。换模型能通过近期原话正确回答王小明，但 `memoryUsed:[]`，不能计作正式决定采用。
- **期望**：已明确确认的决定形成可查看、可溯源的正式记忆，并在换对话、换模型后采用。
- **成绩**：本轮八步 **6/8**，第 03、04 步失败；纠正、重启、遗忘及真实 Core 停止后的降级通过。没有把“回答正确”写成“全部正式形成”。
- **定位**：`src/personal-memory` 的确认边界上下文；Core `memoweft/integrations/hermes/batch_adapter.py::_parse_item` 在 `formed_by == "confirmed"` 且 `context_by_id` 缺上下文时返回 `assistant_claim_context_missing`。本轮已记录实际作业与原话，尚不能把上游缺上下文的全部原因确定为宿主或 Core 单方。
- **证据**：[原话、回复、作业及来源](m2/baseline-mimo.json)、[后续来源页](m2/mimo-sources.png)。来源图属于后续纠正步骤，不冒充“缺失决定”的截图；缺失事实由第 03 步实际列表和作业记录证明。

## 严重 · QA3-02 · 迁移 Verify 向受保护配置接口匿名请求，返回 401

- **端**：Windows 安装版与迁移脚本。
- **步骤**：指定备份只读复制到临时目录；`Prepare -Rehearsal`；真实源码和安装版使用同一副本启动并登录；把配置端口设为本轮实际随机回环端口；调用原脚本 `Verify -Rehearsal`。
- **实际**：安装版已启动、原账号替身登录成功，`scripts/migrate-installed-desktop.ps1:69` 的匿名 `Invoke-WebRequest` 请求 `/personal/v1/config` 返回 **401 Unauthorized（未授权）**。脚本无法完成迁移验证。
- **期望**：验证应使用实际公开且适合健康检查的接口，或明确完成既有鉴权；不能在正常登录宿主上必然被拒绝。
- **定位**：该脚本的 `Verify` 分支。未修改产品脚本、未停用日用任务、未向日用端口请求。
- **证据**：安装与副本演练结果位于 [installed](installed/)。个人备份内容、私有诊断原件与对话截图不公开，只发布布尔验证、错误码及哈希一致性汇总。
- **其他边界**：原脚本明确拒绝 `Apply/Rollback -Rehearsal`，要求使用集成运行器。因此本轮验证了真实安装与同目录源码回退，但没有把它说成真实计划任务的 Apply / Rollback 已验收。没有为测试删除这个保护或创建、控制日用计划任务。

## 一般 · QA3-03 · 网页成文仍有缺少条件的技术断言（BL-18）

- **端**：Windows / MiMo 原 `action-02-web-document`。
- **步骤**：搜官方资料，对比 Node.js 24 与 22，保存中文说明并读回。
- **实际**：本次 174.759 秒完成文件与读回，比 QA2 的 710.981 秒明显短；文档仍声称原生扩展需要针对 Node 24 重编译，并把编译 Node.js 的 ClangCL 要求扩展到所有相关原生模块。漏掉 Node-API 的 ABI（应用二进制接口）兼容例外。
- **期望**：区分 Node 本体构建、依赖 V8 接口的扩展和使用稳定 Node-API 的扩展，避免无条件要求用户重编译或更换全部编译链。
- **核对**：官方 [Node-API 文档](https://nodejs.org/api/n-api.html#node-api)明确说明其跨主版本兼容目标；[Node 24 发布说明](https://nodejs.org/en/blog/release/v24.0.0)中的 ClangCL 要求指编译 Node.js 本体。原成文保留，未替模型修稿。
- **证据**：[原文件](m1-mimo/node24说明.md)、[原结果](m1-mimo/results.json)、[真实对话截图](mimo-action-02-web-document.png)。
- **判据差异**：原自动成绩因 `reply_matches` 要求“说明 / 保存 / 写好”而失败；实际回复说“已完成”并列官方链接。文件与终态通过，不能把这个文字匹配失败误写成没有生成文件，也不能因此宣称全文正确。

## 一般／回归验收失败 · QA3-06 · BL-19 的 macOS 滚动几何断言仍失败

- **端**：macOS上的共用桌面网页 Electron 测试夹具，**不是 SwiftUI 原生Mac窗口**。
- **步骤**：原样运行 `node --test tests/personal-desktop-motion.test.ts`；展开执行进展后，比较 `chat-scroll` 当时与260毫秒后的滚动几何。
- **实际**：`scrollHeight` 都为827，`scrollTop` 从0变为72，原稳定性断言失败。规范化临时目录后的本轮运行9.650秒，0通过／1失败；与BL-19既有失败一致。
- **期望**：原用例要求动效期间滚动指标保持稳定。是否与贴底策略冲突、应如何处理，由后续产品修复包判断；本包没有放宽断言或改产品。
- **定位**：`tests/integration/ui-p1-desktop-motion.mjs:206` 与进展展开／贴底逻辑。原生Mac六条流程的通过不能替代这项回归。
- **证据**：[本轮日志](apple/mac-motion.log)。该命令按原测试使用 `--verify-only`，没有生成截图，不用SwiftUI截图冒充该夹具失败画面。首次因非规范临时路径触发私有目录检查，改用 `/private/tmp` 后才取得上述有效结果，[环境记录](apple/mac-motion-environment.log)另存。
