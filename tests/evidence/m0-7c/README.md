# M0-7c MiMo 场景对照

2026-10-08，使用真实 Electron（桌面程序框架）、固定 DSH（执行框架）、隔离 `eval-` 测试账号与独立 MemoWeft Core（记忆核心）数据。Qwen 基线沿用 [M0-7b](../m0-7b/README.md)，本包只补跑对照，不修改生产代码。

复跑入口：`node tests/integration/personal-scenario-baseline.mjs --mimo --mimo-machine`。MiMo 为 `https://api.xiaomimimo.com/v1` / `mimo-v2.6-flash`；密钥从 Windows Machine（系统）环境的 `MIMO_API_KEY` 读入进程内存。memory-03 第一轮为 `http://127.0.0.1:8081/v1` / `qwen3.8-27b-original`，密钥从 User（用户）环境的 `MODEL_SWITCH_UNIFIED_KEY` 读取；第二轮在同一账号的新对话换成 MiMo。该场景后台路由跟随各轮绑定模型，其余场景后台固定 MiMo。没有读取或解密日用宿主保管库，没有自起模型或请求其他本地模型。

10 个自动场景各执行一次；两个跨端场景仍标需人工，步骤沿用 M0-7b 的 Android/iOS 实机验收说明。场景目标、检查、审批决定及校准时限保持：整理/读代码 360 秒，联网/脚本 900 秒，停止/删除/两轮记忆 600 秒，三轮纠正 900 秒。每个场景的准备、全部回合及检查共用预算。评测器不自动回答澄清，也不批准未声明审批；可选 LLM judge（模型评判）未启用，`memory_used` 采用依据缺少契约支持时仍记不支持。

## 已观察到的记忆接线问题

隔离 Core 2.0.0 正常启动，列表/来源/纠正能力可用，但 MiMo 后台配置下初始状态为 `degraded`（降级）、`MEMORY_MODEL_UNAVAILABLE`、`capabilities.inject=false`、`worldRevision=0`。入口保留这个状态并继续评测，不把降级当就绪或跳过记忆检查。

只读定位：WeftMate `src/personal-memory/index.mjs` 将已选路由和凭据传给 Core 初始化；当前 Core `default_one_shot_route` 的 `cloud`（云模型）分支却仍读取旧 `DEEPSEEK_API_KEY` / `DEEPSEEK_BASE_URL`，不采用传入的 `api_key_override` / `MEMOWEFT_BASE_URL`，缺少旧配置时返回空路由。没有向隔离宿主添加旧 DeepSeek 凭据，也没有把 MiMo 伪装为本地模型来绕过问题。待查通用云模型接线，本包只记录。

正式场景前有两次宿主准备退出：一次未绑定默认后台而无法在无会话时就绪，一次选 MiMo 后报告上述降级。两次均未发送场景消息、未调用模型聊天 API（应用接口）；凭据均由退出清理移除。正式场景没有重跑。

## 办事失败现象

- action-04：MiMo 写出含 `const name = arguments; // placeholder removed below` 的未完成 `sum.mjs`，然后用 `write` 覆盖修正，触发 `[weftmate:overwrite]` 审批。场景未声明这次审批，评测器留下待处理并取消自己的回合；`result.json` 不存在，没有实际营业额成果。Qwen 则在运行包含动态 `outPath` 的脚本时触发覆盖审批。两边都失败，按 D4 列待查代码问题：已有文件修正/动态写入目标与审批政策的交互；MiMo 未完成脚本也是已观察到的模型行为，不能据此跳过产品问题。
- action-06：MiMo 首轮 `pwsh` 删除请求得到 `allowed-once`（允许一次），原生详情 seq 96 随后返回 `Error: unknown tool "pweff"`，文件没有删除。模型重试同一删除命令，seq 139 再次请求审批；场景每轮只声明一次决定，第二张留下待处理，未进入拒绝轮。只读详情从现有 `/personal/v1` 读取，没有代答或追加允许。Qwen 的首轮允许/删除/终态通过，第二轮澄清超时；两边均不过，按 D4 列待查工具调用/执行接线及澄清交互，不宣称两边同根因。

- memory-02：MiMo 首轮将运动偏好写入 `preferences/exercise.md` 并完成，第二轮想把周三改成周五时覆盖该文件，触发未声明 `write` 审批，未进入第三轮。Qwen 同样因覆盖自己的会话偏好文件失败。按 D4 列待查代码问题：真正记忆纠正接线与文件覆盖政策的交互。
- memory-03：严格 Qwen → MiMo。两轮都 `completed`（已完成），MiMo 新会话回复未含“小禾”，`reply_contains` 失败；`memory_used` 仍不支持。此前缺失第二模型的场景已经实际执行，但没有通过跨模型记忆验收。旧 Qwen 栏的不支持仅代表 M0-7b 未配置 MiMo，不能把本次混合模型结果拿来做纯模型能力归因；通用云模型形成/注入接线待查。
- memory-04：MiMo 首轮提问要求选择设提醒/只记录备忘/起草沟通消息，并询问周六提醒时间；没有进入新会话。Qwen 首轮同样要求选择提醒/清单/记住。按 D4 列待查代码问题：人物背景形成/注入与澄清交互，不自动代答来掩盖失败。

## 文档内容抽查

action-02 的确定性检查只覆盖保存、官方链接、回复与终态。MiMo 文档的 V8 13.6、npm 11、AsyncContextFrame、URLPattern 等主要变化与 [Node.js 24 官方发布说明](https://nodejs.org/en/blog/release/v24.0.0)相符；支持周期与 [官方 schedule.json](https://github.com/nodejs/Release/blob/main/schedule.json)相符。但把 Node-API（原生扩展接口）也笼统归为升级大版本必须重编译不准确：[官方 Node-API 文档](https://nodejs.org/download/release/v24.21.0/docs/api/n-api.html)说明其跨版本 ABI（应用二进制接口）稳定性。不修改原通过成绩，也不宣称全文事实准确性已通过。
