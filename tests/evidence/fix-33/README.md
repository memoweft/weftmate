# FIX-33 手机连接电脑主路

原生旁聊把 `chat.message` 当作通用发送命令，电脑返回 `CHAT_UNAVAILABLE` 后又被保存为 uncertain（结果待核对）；原生新对话始终在手机本地创建，缓存登录恢复、Android TLS（传输层安全）信任和新版模型目录探测还分别阻断了旧电脑连接。
合成环境中主对话首条和后三条都成功，旁聊首条也失败，因此原现场“第一条成功、后三条失败”的唯一切换原因仍不能由无路径日志证明；另在真实账号复现了首条回复后发送锁仍未释放、后续点击被忽略的独立问题。
修后真实专用账号连接 preview.6，首条和连发三条均由电脑 MiMo 回答，新对话默认交给电脑；聊天无需两端同时升级，旧电脑自动显示手机独立历史和旧界面问题仍需要电脑更新。

**环境与证据边界**

`versions-before.json` / `versions-after.json` 是实际归档 `3062ea4a` 与当前电脑接口的发送矩阵；修前旧、新电脑旁聊各四次 HTTP 404，修后主对话、旁聊各四次全部接受。合成 backend（后端）只用于这组命令状态复现。

`versions-ui-before.json` / `versions-ui.json` 使用实际固定版本 DSH（助手运行时）和合成 HTTP 流式模型、随机端口、临时目录、独立合成云账号。修前当前电脑源码基准为 `d254f387`；两份计时均使用当前手机网页，分别加载相应电脑 UI（界面）。电脑窗口是真实 Electron，测试专用入口自动附加桌面认证；登录通过真实云注册、电脑绑定、手机连接与内容 Cookie（会话凭据）接口完成，未逐屏驱动生产 Electron 登录窗口。手机网页为当前远程访问 UI，而不是完整手机独立模型壳。B 类测量从已完成一轮的 `/sync/events` 上传开始，不能把它说成完整手机模型结束至窗口可见的测量。

`native-live-after.json` / `native-live-requests.json` / `native-live-computer-starts.json` 来自本人授权、已登录的测试账号和安装版 preview.6；只保存计时、状态、字段名、脱敏路径、模型品牌和事件元数据。手机模型为电脑已有的 MiMo 配置。这组没有操作安装版电脑窗口，电脑窗口可见时间和电脑发消息反向时间未在真实账号上测量。逐屏原图留在本包 `.local/fix33/live`，不公开含账号或设备信息的原图。

**根因和请求形状**

| 位置 | 修前假设 / 失败 | 修后行为 |
|---|---|---|
| `NativeChatModel` / `NativeHostChat` | 所有电脑聊天都用 `chat.message`；旁聊对象不能作为主对话目标 | 主对话 `chat.message + chatId`，旁聊 `session.message + sessionId` |
| `SharedChat` | 明确 404、400 等拒绝也进入未知结果，持续“自动续查” | 明确拒绝终结、保留草稿并显示人话；网络/回执未知保留同一请求，手动核对，不能默默创建第二条 |
| 原生发送锁 | 收到持久回执后仍等附件、历史、审批等串行读取才解除 | 202 持久回执后立即释放发送；后台刷新不会阻止下一条排队 |
| 原生新对话 | 一律 `phone.new`，连接标识和真正执行端不一致 | 在线目标电脑创建会话；无电脑或离线才由手机回答，已有手机对话说明来源 |
| `cloud-account.js` 缓存分支 | 恢复缓存后直接返回，没有初始化云连接和重新进入已认证电脑 | 恢复后配置连接、验证已有内容 Cookie、续接电脑；暂时失败保留缓存 |
| `CloudLogin.kt` | 自定义信任管理器缺 Android 主机名感知的三参数方法；每次请求还重建 SSLContext（安全连接上下文） | 标准证书链/主机名检查后校验 pin（证书公钥固定值）；同 pin 复用工厂，换 pin 删除旧缓存 |
| 内容通道 / 离线同步 | 只见云端 `multiHost`，未先确认那台电脑的能力 | 读取目标电脑自己的 `/cloud/config` 能力，缺省完整旧路，不试 `/auth/cloud-channel`，不发送新版离线字段 |
| 模型目录 | MODEL-1 的 `/model-services` 探测在旧电脑 404，打断初始化 | `/status personalCapabilities.modelServices:1` 才启用目录；旧电脑直接沿原模型接口，新增管理功能说明需要更新 |
| 手机独立记录同步 | 回复结束没有即时补交；电脑不被新同步事件唤醒 | 回复结束触发一次补交，真实新事件推进水位并唤醒既有等待，重复上传不唤醒 |
| 交接卡片 | 共享主题把下拉、菜单、次级按钮也全部强制白字 | 仅主按钮使用白字；下拉用现有选择控件，空模型名给可读占位 |

实际旧电脑主路请求是 `POST /personal/v1/commands`，主对话字段名为 `requestId,targetDeviceId,kind,chatId,modelProfileId,text,mode`；旁聊用 `sessionId` 替代 `chatId`。HTTP 202 返回 `command`，随后用原请求编号读取 `/commands/by-request/<id>`；旧回执含 `commandId,requestId,kind,sessionId,state,receiptId,dshTurn` 等字段，完整各次字段名在 JSON 中。原生最终四条发送 POST 为 403、407、374、380 毫秒，无先行内容认证或不存在回执查询；已有请求重试才先查原回执，不以新编号重复执行。

**原始九次云 400 的结论**

原现场只有 `route:cloud,status:400`，没有路径、错误码或请求关联号，仍不能唯一定位那九次是哪一个接口。本包没有把电脑内容接口的 404 冒充成云 400。真实复验另确认过控制凭据交换返回 `CLOUD_TOKEN_INVALID`，其上游为 `/personal/v1/cloud/oidc/token` 的 `invalid_grant`；这可以解释该次交换失败，却不能据此断言就是原始九次。DPoP（请求密钥证明）首次 nonce（一次性挑战值）也可能产生预期 400，必须有路径和错误码才能区分。最终聊天复验未出现 400/401，已有有效内容会话可直接使用，不因控制凭据暂时失效而退出登录或挡住聊天。

**同步方式和耗时**

电脑内容按持久事件/变化水位同步，能力允许时复用长轮询：网页等待 30 秒，原生等待 15 秒，内容到达立即唤醒并续订；老版 `replyWait:0` 走原有刷新节奏。共享网页流式 250 毫秒、空闲 1500 毫秒、旧兼容 3000 毫秒，原生旧电脑运行中 250 毫秒、空闲 2500 毫秒，这些间隔未调密。中继恢复沿原重连策略，恢复后立即续接有效内容会话，已有等待随变化水位重订阅，没有加一段固定“等恢复”延迟。

手机独立回复在结束时触发上传；原有 20 秒定时器是记忆提取，仍保留，但不再挡住记录同步。新的 `phoneSync` 水位通过已有账号变化等待通知电脑，不新增空闲轮询。遮住原生聊天的旧网页暂停历史/旁栏/动态读取，手机引擎保留；后台和息屏没有加读请求。BL-29 的原有预算测试保留：网页前台空闲 30 秒预算仍是主路 60 / 兼容 66，隐藏态不超过 3；本包没有提高上限。

**设备核对与文案待本人决定**

补充截图确认本人所谓“确认设备弹窗”就是“在电脑继续”卡片，不是登录批准。本包没有加登录前设备审批。设备核对可选方案一：登录完成后在手机做一次不挡路的目标电脑核对，减少“连的是哪台”的疑惑，但新增提示；方案二：只在设备页核对并显示选中目标，登录/聊天更直接，但首次信任说明不突出。交接卡片文案建议：“这段之前由手机回答。继续后由这台电脑回答，原消息和图片都会保留。”仅为建议，没有自行改定稿。

**iPhone 要照查的清单（本包不改 iPhone 代码）**

1. 目标电脑缺省能力时零 `/auth/cloud-channel`、`/model-services`、新版离线字段；不能只看云 `multiHost`。
2. 主对话与旁聊命令分开，同编号重试只核对原回执；pending（排队中）可继续排队，明确拒绝终结，未知状态有手动核对/保留草稿。
3. 在线电脑的新对话默认电脑，已有手机独立对话明确来源与继续入口；无电脑/离线顶栏别暗示电脑在回答。
4. 有效内容 Cookie 优先续接，控制交换失败不抹登录；取消旧异步读取不覆盖新会话，隐藏 WKWebView（苹果网页容器）停止重复历史读取。
5. `phoneHistory` 是电脑只读历史，沿电脑时间线读；不能因 `source:phone` 就当本地记录。
6. 回复结束上传一次，既有等待收到水位变化立即读取，重复上传不唤醒；前台/后台空闲预算不提高。
7. 用新手机×旧电脑×新云，以及三端当前版本，分别测首条+三条、双向≤2秒、独立轮结束≤5秒；明确旧电脑需要更新的界面和同步段。
