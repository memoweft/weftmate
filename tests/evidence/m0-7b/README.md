## 实测发现的代码问题

action-04 初轮42.79秒误报覆盖审批：PowerShell（Windows命令行）输出字符串 `"$u -> ..."` 的箭头被当成 `>` 文件重定向。修复仅在PowerShell工具参数内区分引号文本与真实操作；双引号中的 `$(...)` 执行体、实际重定向、已有文件覆盖、删除及显式启动内层shell（命令解释器）的审批仍保留。评测器没有批准这条未声明审批，原失败保留。

修复后的独立action-04补验仍失败203.43秒。sum.mjs已存在，读取sales.csv并计算茶25、咖啡24、合计49；运行前因 `writeFileSync(outPath, ...)` 的动态目标触发覆盖审批，result.json未生成。策略不能静态解析该变量，评测器没有放行未声明审批；不因单测修复就把该场景改成通过，也不把脚本预计算结果当已执行。MiMo对照缺失时，保留为目标识别/策略局限待归因。

最新成绩：Qwen办事4/6（66.7%）；12项为通过4、失败5、需人工2、不支持1。场景耗时与逐项检查见verification.json及STATE。memory-01第二轮缓存上下文提问超时；memory-02更正会话偏好文件时触发真实覆盖审批；memory-03因MiMo未配置未走第二轮；memory-04首轮询问要提醒、清单还是记住，未进入新会话。结束时隔离Core就绪、worldRevision=0；不声称记忆闭环已通过。

## 时限与结果解释

场景JSON子集不接受传统YAML注释，依据写在各文件 `notes` 中：单轮整理/读代码360秒，联网检索/脚本900秒，停止续做/删除两轮600秒，两轮记忆600秒、三轮纠正900秒，人工跨端600秒。均为准备、全部回合和检查共用预算。慢速样本约6–13 tokens/s，首轮约8.5K预填充出现过79 tokens/s；后续缓存命中会更快。保留原目标、所有检查和声明审批。

`verification.json` 保存去除测试路径、完整回复、账号和会话标识后的成绩、检查与时间线；原始报告、宿主日志和仅计时/计数的请求观测保留仓库外。`memory_used` 仍为unsupported（缺少采用依据），不凭关键词把记忆计完整通过；未启用的可选LLM judge（模型评判）记为skipped（跳过）。

action-02 的确定性检查通过只证明保存、官方链接、回复和终态。人工抽查发现文档把Node22仍需 `--experimental-require-module` 开关写成普遍事实；[官方Node22文档](https://nodejs.org/docs/latest-v22.x/api/modules.html#loading-ecmascript-modules-using-require)明确22.12.0起不再需要该开关。文档也自填了2026-07整理日期。原成绩不改变，但不能据此宣称事实准确性全部通过。[Node24发布说明](https://nodejs.org/en/blog/release/v24.0.0)支持文档的V8 13.6、npm11、AsyncLocalStorage及URLPattern摘要。

两条都需分别在Android和iOS实机验收，使用新隔离宿主、`eval-`测试账号、系统临时目录和指定模型。宿主电脑保持在线，手机连接该隔离宿主，不接本人日用数据。

1. cross-01：在电脑临时目录写入场景 `setup.files` 的待清理文件；电脑WeftMate程序发送原目标，手机同账号打开同一对话。确认实时步骤和原位删除审批可见，在手机允许一次；确认电脑文件删除、两端原对话出现终态。保存两端截图与耗时。不能以评测器代点审批替代。
2. cross-02：电脑临时目录写入备忘文件；手机发送原目标；观察电脑执行，手机原对话显示成果卡。打开实际购物清单核对牛奶及 `- [ ]`，返回原对话确认completed（已完成）。保存手机成果打开与电脑执行截图、耗时。
