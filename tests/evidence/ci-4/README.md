第 1 条没有证据表明是 MEM-7 引入的产品阻塞；已确认是测试把首次私有目录／工作器初始化算进了 2 秒形成等待断言。MEM-7 的父提交与当前实现都通过同一固定时钟证明：初始化单独消耗 2100ms、形成任务轮询为 0，旧起点仍超期；准备与测量分开后原断言成立。#289 首次实际失败是默认不等待分支，显式期限分支当次通过；#294 随后才出现显式期限分支失败。

本包没有删除用例、增加 skip（跳过）、放宽原预算或扩大计时重跑清单。N4 从原文件移入独立文件并作为完整 vendor 文件登记；因此 required（必过组）不会执行其准备钩子。云端自动重跑沿用原最多一次规则，vendor 仍严格单次。

本机使用隔离目录、随机端口、合成身份，无真实模型请求。初次验证中本包先把原始 `mkdtemp` 目录交给托管删除器，造成归属错误；已改为配套托管创建，并收集该次留下的两个已知测试进程。该次失败保留在本机日志，不计入通过数。

首份 `fc75a5ba` 云端验收在 macOS 的 `folder-choice.test.ts` 发现另一处明确夹具矛盾：它对 Darwin（macOS 平台）期待201，但注入检查器对所有非Windows平台都抛 `PROJECT_WINDOWS_REQUIRED`。本包仅修正该检查器的支持平台及路径格式，所有权限／版本／浏览器路径隐私断言保留；不改Apple产品。旧首轮失败与其余已通过工作流保留，停止原控制器防止继续触发旧代码；修复后另起固定提交三轮，不能把旧首轮计入最终成功轮。

`a6942c49`三轮保留在 [退出修复前](before-desktop-exit-fix/three-rounds.md)：第1轮七工作流全过，第2轮图库手机深色rendering超时，第3轮macOS的M1桌面错误探针110秒超期。其8个错误／恢复场景的全部数值满足原请求数／恢复断言，脚本已写报告，随后仍以SIGTERM（终止信号）等待合成Electron退出。本包仅将该探针改为关闭生产控制器后app.exit(0)，沿用N4／同步探针已确认的退出方式；原110秒／120秒、八场景、请求数／2秒恢复断言不变，Windows实际单项61秒通过。新代码另起同提交三轮，不能把旧轮次当新代码通过。
