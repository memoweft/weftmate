## 分段与根因

2000会话的创建窗口20次分段，单位毫秒。各层嵌套且后台活动交叠，不能把不同层p95相加。

列表调用次数来自长度不同的创建／切换窗口，不能直接当作同比调用率；单条核对不全枚举另由定向测试验证。

主要根因为原生预设发现扫描随会话数增长，另有全枚举身份核对和250毫秒回执轮询。复用只用于宿主生成的 personal-remote / personal-shared-chat，预设文件变化重新挂载；标记取挂载前，避免中途编辑使旧挂载被误记为新版本。缓存只持有本生命周期仍拥有的会话编号；来源被删除／遗忘后不复用已释放句柄；其它预设保持原发现规则。

HTTP（网页请求）等待选项在串行提交队列外等既有调度完成，最终回执写盘后才返回，原30秒调度期限、崩溃安全和幂等身份不变。45秒客户端超时／断线保留原请求，重新查询回执；成功回执之后还要读单一聊天实体、选中并恢复草稿才解锁。确定失败按同一请求编号清掉发送锁。新增最终写盘失败测试：返回dispatching，重启转uncertain，原生创建不重放。

剩余规模增长主要在DSH JSONL（逐行JSON）日志的findLog／项目目录扫描，以及状态完整克隆、验证和序列化。2000尾部CPU采样中exists占约35.8%、findLog约26.8%的样本（调用栈包含关系，不能相加），详见 [原生采样](tail-profile-complete/native-stages.jsonl.cpuprofile)。此次不绕过原生唯一身份／编码与坏日志校验，不修改固定vendor（运行时依赖），也不为几十毫秒落盘成本改写存储。后续建议在DSH原生持久层做可重建的精确日志位置索引，同时保留跨项目重复身份与损坏日志检查；500的偶发尾部已定位到单一历史Gateway（网关）等待，尚未单独拆分该样本的处理器排队、磁盘I/O（输入输出）和路径查找份额；不将它断言为预设问题。后续为单历史请求加原生分段／冷暖缓存对照。
