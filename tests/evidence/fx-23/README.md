结构化证据见 [package-chain.json](package-chain.json)。全部账户、模型响应、目录与安装身份都是合成数据，真实模型请求为 0；没有访问日用宿主、数据或保管库，没有请求 8081／18186，没有正式发布、上传或注册正式安装项。

## 故障与处理

FX-22 将所有 Windows 用户目录路径一律拒绝，命中了第三方 node-pty 测试源码中的上游作者示例路径。依赖预检只检查依赖来源及安全公告，普通单测没有构建安装包，本机旧夜间启动器又没有执行这条链路，因此缺少真实打包的云端红灯。

选择分层检查：自有代码、插件和配置仍拒绝任意用户目录；第三方依赖全部检查操作系统实时读取的本机用户目录、用户名、机器名及构建目录。没有白名单单个文件，没有跳过 node_modules（第三方依赖目录）。另一方案是删除第三方非运行时源码；node-pty 的入口在 `lib`，暂存时裁剪 `src` 不会改变原始 tarball（依赖包归档）的哈希或包集合，但需额外维护裁剪规则。本次保留源码与已验证的运行包，只去除包管理器安装状态、缓存与机器专属命令快捷脚本。

扩大扫描后发现并修复了真实残留：get-windows 重编译中间文件和原生调试路径、旧插件写死的个人欢迎语、pnpm（依赖管理器）安装元数据，以及 DSH CSS（样式表）虚拟模块注释中的构建绝对路径。包使用 N-API（跨 Node 版本原生接口）预构建；CSS 标识改成仓库相对路径，真实读取和变更监听保持原物理文件。原始 vendor（固定运行时）tarball 哈希、依赖闭包、单实例及真实启动验证全部通过。
