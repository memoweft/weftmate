# MEM-7 验收证据

手机原对话沿 `/offline/turns` 进入已有 MEM-1（聊天导入）持久任务，再由真实 Core（记忆核心）形成正式记忆。手机轻量条目只留本机，采用 APPLE-7 的规则，电脑接收的是原对话。PR（拉取请求）：[#289](https://github.com/memoweft/weftmate/pull/289)。

`acceptance.json` 是一次已通过的真实 Electron（桌面程序）＋固定 DSH（助手运行时）＋真实 Core＋随机端口合成云／合成账号结果，成功轮 66 次 MiMo（云端模型）请求。`attempt-*.json` 保留失败与成功调试记录；不能把失败候选图当作通过证据。`model-requests.json` 汇总 28 次已记录尝试共 302 次推理请求；服务商打断前来不及保存的请求不能推算成精确数。密钥只从机器环境读进父进程内存，不落日志或配置，合成代理凭据不是真实密钥。

真实闭环检查：

- 手机注册无电脑账号，配手机模型，聊天明确说“我叫林舟”、鹦鹉“青瓷”、喜欢茉莉花茶和正在做“纸舟”练习项目；随后改口喜欢乌龙茶。轻量记忆页能读到条目，新对话能使用新偏好。
- 真实电脑登录同一合成账号，先配置标为本机类型的隔离回环模型代理；没有云模型时仍取得 `model:null`、接收公钥及 `memoryAuthority.ready`。这是模型选择与接收解耦的证明，实际推理传输仍为 MiMo，不能声称本地 GPU（图形处理器）推理已经验收。
- 原对话进入 MEM-1 后由真实核心形成；电脑历史可见、可搜索且只读，消息可以开原生旁聊，来源引用保持稳定。
- 电脑主对话回答：“你叫林舟；鹦鹉青瓷；现在更喜欢乌龙茶、已不再喜欢茉莉花茶；正在做纸舟练习项目。”结果不是替身注入，查询只用核心按权限过滤的原快照。
- 从导入记录整批忘掉后，同一主对话再问得到“没有可核实的记忆内容，无法作答”。手机原对话仍保留。
- 40 段约 300 KiB（千二进制字节）的历史走了等待确认、显示预计用量、开始、暂停、继续、完成；7 个验收检查全部通过。
- 关闭浏览器后扫描该合成账号的 7 个 IndexedDB（浏览器结构化存储）文件，条目正文的 UTF-8／UTF-16（字符编码）明文命中为 0。

`phone-{360,390}-{light,dark}-*.png` 为真实闭环的手机网页内容区图；`electron-{1200,480}-{light,dark}-*.png` 为真实桌面程序图，共 60 张。早期手机编辑框和桌面旁聊表单样式候选被最终修正替代；大量确认阶段旧图可能没有滚动到新增记录，不单独作为确认文案的证明。真实行为由 `acceptance.json` 中大量流程检查证明。

`ui-final-*.png` 与 `final-ui.json` 是最终样式的单独呈现验证：实际 Electron／手机网页组件，合成呈现数据，0 次模型请求，16 张图。桌面使用当前完整产品样式和 Windows（视窗系统）界面模式，补拍了大量等待确认／用量弹层及来源旁聊；手机补拍编辑弹层。它们证明当前呈现与控件样式，不能替代真实核心闭环。

产品与模型质量边界：

- 已实现稳定电脑会话回执和手机“已在电脑上”；直接在原只读历史线程继续聊尚未接线。现有原生旁聊带来源引用，显示“相关上下文尚未带入”，未虚构已经复制上下文。
- 按 APPLE-7 对齐要求，全部 `synced`（持久接收）回执即清轻量条目。未交／部分确认保留轻量条目；全接收而大量任务尚待确认或整理时，可能暂时无正式记忆。这与最初“无空窗”的目标有差距，建议两端一同以完成形成状态作为清理条件，当前未单独改变网页端。
- 真实 MiMo 曾输出缺 `invalidate`、无效 JSON（结构化输出）及新增 `id:""`；前两类静默保留水位再试，最后一类按 iPhone 既有实现忽略该更新却推进水位，可能漏记。保留失败记录，建议两端共同拒绝不可用标识并使用严格输出格式，当前不放宽校验。
- 健康等敏感内容的输出正文也按原生规则要求明确“记住”措辞，可能保守漏记；不单独改变一端。
