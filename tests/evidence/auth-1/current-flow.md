# AUTH-1 改动前的身份与登录链路

以下记录基于 `fa6d96a8`，仅描述原来的流程。

| 身份或凭据 | 保存与核对位置 | 原来在哪一步检查 |
|---|---|---|
| 本地账户与密码散列 | 宿主 `store.json`，`authentication.mjs` | `/auth/setup|register|login`，Cookie（会话凭据）的本地认证代际；已有数据以 ownerId 隔离 |
| 云账号邮箱、密码与邮箱码 | 云 `cloud_accounts`、`email_challenges` | 登录、注册、找回；新设备标识或新公钥第一次密码登录追加邮箱码；原来没有纯码登录 |
| 云端设备号与指纹 | 云 `cloud_devices`，宿主身份日志 | 云记录已邮箱确认的设备；宿主按云设备号和公钥指纹寻找内容信任 |
| 设备私钥、公钥及 DPoP（设备密钥持有证明） | 桌面系统加密存储、手机安全层、网页不可导出密钥；云/宿主核对公钥 | 授权码兑换、刷新、控制面请求；宿主额外核对方法、精确地址、令牌摘要、一次性挑战与重放 |
| 宿主对设备的 pending/trusted/denied/revoked 状态 | 宿主 `cloud-identity/identity.json`；最小状态同步云 | 云登录之后交换内容会话；新设备一律 pending（等待批准），另一已受信设备或当面配对才能进入 |
| “离线/应急密码” | 同一个本地账户的密码散列；绑定中记录是否设置过 | `/auth/cloud-offline` 只选本机绑定，再走本地密码校验；它不是云密码，也不是额外加密钥匙 |
| 可信交付码与配对材料 | 宿主安装签名、公钥、TLS（加密传输）公钥指纹；客户端保存 pin（证书固定） | 已批准设备通过另一已受信通道或电脑二维码取得宿主锚；新设备登录页等待这一步 |

| 原来的登录入口 | 原来实际走的路 |
|---|---|
| Windows 原生窗口 | `weftmateDesktop.identity` → 共用 cloud-account → 云授权/密码/新设备邮箱确认 → `/auth/cloud-desktop`；活激绑定下陌生密钥返回等待批准；离线入口另走本地密码 |
| 手机网页/其它电脑，经宿主中继 | 云授权/邮箱密码/新设备邮箱确认 → 宿主 nonce（一次性挑战）与 `/auth/cloud-session` → 等待另一设备批准及材料交付 |
| Android 原生壳与可更新界面 | 共用登录状态机 → `cloud.app.*` 安全层、已登记云路径 → 宿主云会话；未连接宿主的旧适配器也投影 pending_approval |
| macOS/iOS/watchOS | Apple 原生 `CloudLoginModel` / `CloudAccountClient`，App 内密码/邮箱确认与 PKCE（授权码校验），原生安全存储与宿主 pin；配对/批准等待由原生界面处理，Watch 沿已登录手机/原生客户端会话 |

死锁点是宿主第二次检查：云已经核对邮箱和设备，宿主仍要求另一台受信设备；只有这一台电脑、旧密钥不可用时没有可批准的设备。本机窗口还先要求云/本地密码，机主因此进不了已有数据。
